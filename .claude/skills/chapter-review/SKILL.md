# Chapter review

Partition the current branch's diff into logical chapters and hand them to the extension with the `chapter-review` command that sits next to this file. You never read or write the manifest file yourself: `chapter-review write` installs a partition draft, `chapter-review issue …` records findings, and `chapter-review focus`/`show` read back the review state. The command owns the protocol directory (`<git-dir>/chapter-review/`: `chapters.json` for the partition and findings, `progress.json` for the reviewer's checkmarks, `focus.json` for what they're looking at, and a `chapters.json.bak` refreshed before each write), validates every change, and preserves findings and review progress across regeneration — so you talk to the extension, not to a file.

Every hunk must end up in exactly one chapter — or in `unassigned`. The contract is `validate.ts` (authoritative) and `chapters.schema.json` (the same rules as JSON Schema), both next to this file; `example-chapters.json` next to them is a worked illustration. The manifest lives inside the git dir on purpose: it is tool state, invisible to `git status`, and no user-owned file (worktree, `.gitignore`, `.git/info/exclude`) gets touched.

## The command

Resolve the command's *path* relative to this SKILL.md, e.g. `"$SKILL_DIR/chapter-review" <args>`, or `node "$SKILL_DIR/chapter-review" <args>` if it isn't executable. But run it with your **current directory inside the repo you're reviewing**: the command picks its manifest destination from `git rev-parse --absolute-git-dir` at the cwd, not from its own location. In a nested-repo layout (a repo that contains another repo, like a `demo/` fixture) a cwd in the wrong worktree silently writes the manifest into the wrong `.git`. `write` prints the path it wrote — check it. Requirements are `git` and `node` (22.18 or newer) on PATH.

- `chapter-review write [file]` — validate a **partition draft** (chapters + unassigned + meta, *no* `issues` and *no* `reviewed`) and install it. Reads the draft from `file` or stdin. It validates before writing and refuses an invalid manifest. It carries existing findings and the reviewer's checkmarks forward, pruning only entries whose path left the diff, so regeneration never loses review work. It refuses a draft that describes a different tree, so a wrong-directory run cannot overwrite another repo's review. A draft is accepted when its `headSha` **is** the checked-out commit; failing that, when its `head` names a ref pointing at the checked-out commit — and in that case a `mergeBase` or `headSha` naming a commit this repo has never contained is a veto, because two unrelated projects are very often both on `main`. `head` must be a real ref name: `HEAD`, `@` and their relatives (`HEAD^0`, `@{0}`) resolve to whatever tree you are standing in and so prove nothing. Both SHAs may be stale — they get re-pinned — but must be commits this repo has; only `generatedAt` accepts a placeholder. A repo with no resolvable `HEAD` (empty, unborn branch, or `HEAD` pointing at a deleted ref) is refused outright: nothing there is reviewable. It also re-pins the commit metadata (`headSha`, `mergeBase`, `generatedAt`) to the working tree it observes, so a regenerated manifest matches live git and the extension stops flagging the review as out of date. The summary line always opens with `Wrote <n> chapters across <n> files (<n> claims)`. A "claim" is one *enumerated hunk*, except that a whole-file entry (no `hunks` array) counts as exactly 1 no matter how many hunks the diff holds for it — so a file entry listing 3 hunks contributes 3, and a file split across two chapters with one hunk each contributes 2. `unassigned` entries are claims too, and `files` counts distinct paths, so a path split across a chapter and `unassigned` is 1 file but 2 claims. The preserved-counts clauses (chapters kept, issues preserved, pruned, checkmarks carried, checkmarks dropped) are appended **only when non-zero**, so a first write prints the opening sentence alone; their absence means zero, not a missing line. Read "checkmarks carried" as rows that survived path-pruning, not as units that still read as reviewed — see [Regenerating](#regenerating-the-branch-moved). It is not a signal to go unchecking things.
- `chapter-review issue add --path P --severity S --note "…" [--confidence suspected|verified] [--chapter ch-N] [--hunk oldStart,oldLines,newStart,newLines] [--old-path P]` — record a finding. The id (`iss-N`) is assigned for you and the owning chapter is inferred from `--path`. When the path lives in **one** chapter that's unambiguous; when it spans **several** (a hunk-split file), pass `--hunk` to select the chapter that owns that range, or `--chapter` to name it outright — otherwise the command picks the first owner and warns you to disambiguate. `--hunk` does two jobs, and the warning only mentions the first: it picks the owning chapter *and* it is what pins the finding to that range. Omit it and the finding anchors to the whole file, so a finding about one hunk needs `--hunk` even when `--chapter` has already settled ownership. `issue list` prints the range each finding carries, so you can see which of the two you got. A finding defaults to `confidence: suspected`; see step 7. `--path` must name a path the manifest holds, in a chapter or in `unassigned`; anything else is refused, because a finding outside the diff anchors to nothing the reviewer can open. Findings anchor to **chapters only** — `--chapter` takes `ch-<number>`, never `unassigned`. For a path split between a chapter and `unassigned`, the finding lands on the chapter-side owner (that split doesn't count as "spans several", so you get no ambiguity warning); a purely quarantined path has no owner, so the finding is recorded without a `chapterId` and the extension shows it outside any chapter. Don't file findings against quarantined noise — if a lockfile hunk is worth a finding, it wasn't noise.
- `chapter-review issue set <id> [flags]` / `resolve <id>` / `reopen <id>` / `verify <id>` / `unverify <id>` / `rm <id>` / `list` — revise findings in place. `verify`/`unverify` flip a finding's confidence (shorthand for `set <id> --confidence …`). No need to re-send the manifest. `set` takes the same flags as `add` and needs at least one of them, including `--status open|resolved` (what `resolve`/`reopen` are shorthand for); `issue --help` prints them all. A `--hunk` must be one of the ranges the partition claims for that path, copied exactly. `rm` retires the id rather than freeing it, so the next `add` never reuses a number you may already have quoted in a PR comment or report.
- `chapter-review uncheck --path P [--hunk oldStart,oldLines,newStart,newLines]` — clear the reviewer's checkmark on a file (or one hunk) so it reads as unreviewed again. It removes the matching unit from `progress.json`, the same kind of direct edit as `issue resolve`; the extension unticks the box, and if the reviewer re-checks it the extension writes it back. Use it on regeneration for a file whose bytes didn't change but whose correctness now depends on one that did, or mid-review to send the reviewer back to something.
- `chapter-review base-check [base]` — report whether the review base is fresh before you diff against it (read-only: never fetches, never writes). Prints JSON with an `action` (`ok` / `switch` / `fetch` / `unresolved`); step 1 acts on it. Pass the base you resolved to check that exact ref, or omit it to let the command resolve the base the same way step 1 does. **`action` is the only field to branch on.** The rest is diagnostic context for your summary: `base`, `baseSha`, `mergeBase`, `message` (a prose version of the verdict), `remoteReachable`, `remoteTip`, plus `unfetched` (a boolean, always present once the base resolved — `true` is what drives a `fetch` verdict) and `suggestedBase` / `suggestedMergeBase` / `ahead`. Those three appear whenever a fresher local base exists, which is what a `switch` verdict is made of, but they can ride along on a `fetch` too when both conditions hold at once. Their presence is not the verdict; `action` is. On `unresolved` you get only `action` and `message`, plus `base` when a base was named but didn't resolve (when none resolved at all, `base` is absent from the JSON). `stale` is a convenience alias for `action !== "ok"` and cannot disagree with `action`; if you only read one field, read `action`.
- `chapter-review focus` — print what the reviewer is currently looking at.
- `chapter-review show` — print the current manifest.

Every mutating command validates the resulting manifest and refuses to write if it would be invalid, printing the errors. There is no separate validate step to remember.

**One writer per document, one agent at a time.** `chapters.json` is yours; `progress.json` and `focus.json` are the extension's. That split is what lets you record a finding while the reviewer ticks a box without either of you losing the other's edit. Within your half, run the commands **serially** — each one reads the manifest, changes one thing and writes it back, so two of your own invocations racing each other will drop one of the changes and both report success. Nothing enforces this; sequential calls are the contract.

## Steps

1. **Resolve refs, then confirm the base is fresh.** `base` = default branch (check `git symbolic-ref refs/remotes/origin/HEAD`; if this errors for any reason — no origin remote, or an origin that never ran `remote set-head`, which both report `not a symbolic ref` — fall back to `main`, then `master`, taking the first that `git rev-parse --verify` actually resolves rather than assuming it exists), `head` = current branch, `headSha = git rev-parse HEAD`. `base` and `head` are ref names, `headSha` is a full SHA.

   **Keep the `origin/` prefix when `origin/HEAD` resolved it.** Strip only `refs/remotes/`, so `refs/remotes/origin/main` → `base = "origin/main"` — not the local `main`. The tracking ref is the one a PR merges into, it's the fresher of the two whenever local `main` is behind, and it's what a bare `chapter-review base-check` resolves on its own, so recording it keeps base-check judging the same ref you diff against. Only the fallback chain yields a bare local name (`main`, `master`), because there is no tracking ref to prefer. Either form is a valid `base`; if local `main` somehow forks ahead of `origin/main`, base-check reports `switch` and you move to it.

   Before taking the diff, run `chapter-review base-check` (pass your resolved base to check that exact ref, or omit it to let the command resolve it the same way). A stale base is the classic footgun: an unfetched `origin/main` (or a local `main` behind it) pushes the merge base back to an old fork point, so the diff fills with commits already merged to main. The command is read-only and prints JSON with an `action`:
   - `"ok"` — the base is current; proceed. If `remoteReachable` is `false` (an origin exists but the remote couldn't be reached) or `null` (no origin remote is configured), the remote check was skipped — proceed, and say so in your reply to the user, the same way you'd report a `switch`.
   - `"switch"` — a fresher copy of the base already exists locally (`suggestedBase`, forking `ahead` commits ahead of your base). "Fresher" is measured at the fork point with **your** HEAD, not by which ref is ahead in general: a local `main` carrying commits your branch never grew from stays `ok`, because moving to it would not change the diff. Set `base = suggestedBase` and continue. It's a local ref with no fetch, so don't ask — just mention the switch in your reply to the user. (Throughout these steps, "your reply" means prose you write back to the user; the manifest's `summary` field in step 8 is a different thing — a one-line description of the branch.)
   - `"fetch"` — `origin/<branch>` differs from the real remote tip (unfetched). Ask the user with one `AskUserQuestion` whether to `git fetch` the base and regenerate against the fresh fork point, or proceed against the stale base. Fetch only on their go-ahead, then recompute against the moved ref.
   - `"unresolved"` — no base ref resolved. Don't re-run the resolution above; that chain is what already failed. Ask the user for the base with one `AskUserQuestion`, offering any local branch that isn't `head` as the candidates. If the repo genuinely has no other branch, say so and diff against the root commit (`git rev-list --max-parents=0 HEAD`) as `mergeBase`, recording that `base` in the manifest so the reviewer sees what the diff was taken against.

   Then `mergeBase = git merge-base <base> HEAD` against the (possibly switched) base — a full SHA. Diff against `mergeBase`, not `base` — you want "what this branch added", not "what main looks like vs me". Always record `headSha`: the extension reconstructs chapter-scoped diffs from it after the branch moves on. Resolve all of this fresh on every run, a regeneration after the branch moved included (see [Regenerating](#regenerating-the-branch-moved)); never carry a previous run's refs forward.

2. **Pull the diff.** `git diff -M --unified=3 <mergeBase>..HEAD`. `-M` matters: without it a rename shows up as delete+add and can never become `status: "renamed"`. Parse files and hunk headers (`@@ -oldStart,oldLines +newStart,newLines @@`). Header quirks: a count of 1 is omitted (`@@ -3 +3,2 @@` means `oldLines: 1`), and the empty side of an added/deleted file reads `-0,0` / `+0,0`.

3. **Cluster by intent, not by file.** A chapter is what a reviewer evaluates as one unit: "remove legacy X", "add Y", "rename Z everywhere", "tests for Y". One file can split across chapters; one chapter can span many files. Aim for 3–8 chapters on a typical branch — 15 means you're slicing too thin, 1 means too coarse. On a small branch fewer is fine; never pad the count.

   Chapters must be self-contained: the reviewer should see a change *and* what it means in one sitting.
   - Don't split an abstraction from its implementation and wiring. An interface, its first implementation, and the injection sites are one chapter unless each is genuinely large.
   - When the branch replaces X with Y, keep the removal of X visible: either one "replace X with Y" chapter, or a "remove X" chapter directly next to the "add Y" chapter. Never tuck the deletion of X into a chapter whose title is about Y's wiring.
   - A rename that ripples across files is its own chapter, but don't split a file just to relocate a lone rename call-site. When one file carries both a substantive change and a single renamed call-site, keep that hunk with the substantive change; pull call-sites into the rename chapter only when the rename is that file's main change. If that leaves the rename chapter holding only the renamed file itself and no call-sites, keep it — a one-file rename chapter is fine, and its `description` should say where the call-sites went ("call-sites travel with their own chapters").
   - A chapter whose files can't be understood without opening a later chapter is mis-cut.

4. **Quarantine noise.** Lockfiles, snapshot updates, generated code, pure autoformat hunks → `unassigned` with a short `reason`. Don't force these into thematic chapters.

   A generated file's *driver* is not noise: a version bump in a csproj or package.json is a hand edit and belongs in a chapter (its own chore chapter, or the chapter that needed the bump), while the lockfile it regenerates goes to `unassigned` with a reason naming the driver **by path**. Don't cite a chapter id in `reason` prose: ids are stable only within a generation and may be reminted on the next one, and nothing rewrites prose that references them, so a cited id silently goes stale.

5. **Check completeness.** `⋃(chapter hunks) ∪ unassigned == full diff`. `chapter-review write` enforces this for you in the next step: it takes the same `mergeBase..HEAD` diff and refuses a partition that leaves a file or a hunk unclaimed, claims a range the diff does not have, claims a path outside the diff, or gives a file a `status` git disagrees with — naming each offending file and range. Take `status` from the diff rather than deciding it: the extension renders an `added` entry with an empty left-hand side, so a modified file labelled that way loses its before-diff. Together with the structural rules (schema, no hunk claimed twice, no overlapping ranges, no whole-file claim next to another claim, consistent status per path) that is the whole contract, checked on write. There's no separate validator to run.

   Coverage is judged on the lines the diff actually changed, not on hunk spans, so a coordinate that slides off a changed line is caught and named. What it still cannot catch is a range that moves without uncovering anything — widening a hunk, or shifting it across neighbouring context. The extension reconstructs the chapter diff from exactly these numbers, so copy them from the `@@` headers rather than counting lines by hand.

6. **Order chapters as a review flow.** The order *is* the narrative: at every chapter the reviewer should know why they're looking at it. Core change first — the thing the branch exists for, with a preceding removal only when it motivates what follows. Independent side changes (mechanical renames, opportunistic refactors) come after the core story, not before it; leading with a trivial rename buries the plot. Then tests, then docs/chores.

   Story test before writing: read your titles top to bottom. They should work as a changelog that explains the branch to someone who hasn't seen the diff. If any title raises "why is this here / why now?", re-order or re-merge. A tooling or test-framework bump (an xunit upgrade, say) can sit with the tests it supports or as a trailing chore; either reads fine.

7. **Note the issues you noticed.** Partitioning means reading the whole diff, so keep track of genuine problems as you go: bugs, risky changes, smells, or things worth questioning. You'll record them with `chapter-review issue add` in step 9 (it needs the manifest to exist first). Each finding is a `path`, a `severity`, a one-line `note`, and — when it's about a specific hunk of a hunk-split file — a `--hunk`; for a whole-file entry (added/deleted/renamed claimed whole), `path` alone is the anchor, don't invent coordinates. The `iss-N` id and the owning chapter are assigned for you.

   Severity: `critical` = broken or unsafe as written (data loss, security hole, crash on a normal path); `high` = a real bug or risk that bites on a real path; `low` = a smell, gap, or minor concern. Judge the change as written, but don't flag an intentional simplification as if it were a production omission unless the branch presents itself as complete. Flag only real findings; a clean chapter has none, and findings never block writing the manifest. The user reviews these and can ask you to add or revise more later (see Follow-up review).

   Confidence is separate from severity, and the test is **where you had to look**, not how sure you feel. Mark a finding `verified` (`--confidence verified`, or `issue verify` later) only when you went *outside the diff you were partitioning* to confirm it — opened a file at HEAD, traced a caller, or searched the repo. Reading another hunk of the same diff doesn't count; the whole diff is what a partition pass already reads. A finding you can see entirely inside the diff stays `suspected`, the default: the diff shows what changed, not what the rest of the codebase does about it, so "this constructor has no null guard" is plainly visible in the hunk while *whether that's a bug* depends on callers the diff never shows. That's the value — a first-pass note reads as "verify before relying on this" rather than as settled, so a shaky note is never presented as confirmed. It follows that most findings on a partition pass stay `suspected`; that's expected, not a gap. Verifying every one would turn partitioning into an audit, which is not this step's job.

8. **Install the partition.** Build the draft — `version: 1`, `base`, `head`, `mergeBase`, `headSha`, ISO-8601 `generatedAt` (any valid placeholder works; `write` re-stamps it), an optional one-line `summary` (shown as the branch summary in the extension), `chapters` (each with a stable `id`: number them `ch-1`, `ch-2`, … on a first write, and on a regeneration reuse the ids `chapter-review show` reports, see [Regenerating](#regenerating-the-branch-moved)), and `unassigned` — and hand it to `chapter-review write` (write it to a scratch file and pass the path, or pipe it on stdin). Keep that scratch file **outside the worktree** you are reviewing, or pipe on stdin: a draft written next to the code gets picked up by the next `git add -A` and committed into the branch under review. Do **not** put an `issues` or `reviewed` array in the draft; findings are recorded separately in step 9, and the reviewer's checkmarks live in `progress.json`, which the extension owns. The command validates and refuses a broken partition (fix and re-run), then prints the summary line — relay it, don't echo the JSON. On regeneration it carries existing findings and checkmarks forward for you; nothing to preserve by hand. It also re-pins `headSha`/`mergeBase`/`generatedAt` to the commit it sees, so the manifest matches live git and the extension's "Review may be out of date" banner clears once the write lands.

9. **Record the findings.** For each problem from step 7, run `chapter-review issue add --path … --severity … --note "…"`. The owning chapter is inferred from the path; when the path spans several chapters, add `--hunk oldStart,oldLines,newStart,newLines` (selects the chapter owning that range, and pins the finding to it) or `--chapter ch-N` (names the chapter only) — the command warns if it has to guess. Add `--confidence verified` only for findings that met step 7's test — you looked outside the diff to confirm them. Skip this step when the branch is clean.

## Regenerating (the branch moved)

Re-running the skill on a branch that already has a manifest is a normal operation: you regenerate after new commits, an amend, a rebase, or a fetch that moved the base. Resolve refs fresh (step 1) and pull the current `mergeBase..HEAD` diff (step 2) as always, but **don't rebuild the partition from scratch. Reconcile against the one that already exists.** Run `chapter-review show` first, then keep each file in the chapter it already lived in and carry that chapter's `id` across; place only genuinely new material, and mint a new chapter id only for a genuinely new grouping. The aim is a targeted update: the manifest changes only where the branch changed.

Coordinates still come fresh from the new diff (never copy the old ones), but the *assignment* stays put. A file the new commits didn't touch lands back in the same chapter with identical coordinates, so its entry is byte-for-byte the same and the manifest diff stays silent there. A file they did touch gets fresh coordinates in its existing chapter. Re-cluster only when the branch's story genuinely changed, never as a reflex: a gratuitous reshuffle churns ids and the reviewer's checkmarks for nothing. A rebase legitimately rebuilds most of the partition *when the commits it moved over touch the same files you did*; a rebase onto upstream work that went elsewhere often changes nothing but the pin. A lone commit touching two files should change about two entries.

You call the same `chapter-review write` as a first run, and it handles the rest:

- **Commit pin.** `write` stamps the pin (`headSha`, `mergeBase`) and a fresh `generatedAt` from the working tree it observes, overriding whatever the draft carried. This is what clears the extension's "Review may be out of date" banner. Build the partition against the **current** HEAD, since that's what `write` pins to; a stale partition stamped with a fresh HEAD would render diffs against the wrong blobs.
- **Chapter ids.** Reuse them from `show`; `write` installs whatever ids you supply and never renumbers. Stable ids are what keep the extension's collapse/expand state and keep findings grouped without re-mapping, so preserving them is the whole point of reconciling rather than rebuilding. A genuinely new chapter takes the next unused `ch-N`.
- **Findings.** Recorded issues carry forward by `path` (+ `hunk`). With ids stable a finding stays under its chapter untouched, re-mapped only when its path actually moved to a different chapter and pruned only when the path left the diff. A rename is not a departure: give the entry `status: "renamed"` and `oldPath`, and findings and checkmarks follow the file to its new path (`write` prints `followed rename …` for each). Omit `oldPath` and the rename reads as a delete plus an add, which is exactly the review work you were trying to keep. Only a file that existed at the merge base can be renamed in this sense: one the branch added and later renamed appears in `mergeBase..HEAD` as a plain `added` entry under its final name, with no rename for `-M` to detect and nothing for `oldPath` to point at. After writing, add findings for genuinely new problems; don't re-add ones the carry-forward already kept (check `chapter-review issue list`).
- **Review progress.** The reviewer's checkmarks live in `<git-dir>/chapter-review/progress.json`, keyed by content digest, and `write` carries them forward (pruning units whose path left the diff). A file or hunk whose content didn't change keeps its checkmark; one whose content moved reads as unreviewed again. The reviewer resumes on untouched code and only re-reviews what actually changed.

  **Split of labour, so the summary line doesn't mislead you.** `write` carries checkmarks by *path*: it drops the units whose path left the diff and keeps the rest verbatim, digest included. It never recomputes a digest, so it is not the thing that re-opens a changed file. The extension is: it fingerprints the current content and treats a unit as checked only while the stored digest still matches. So `N checkmarks carried` counts rows that survived pruning, and a carried row whose file changed still displays as unreviewed. Both halves are working when a changed file keeps its row here and shows unticked there. Don't "correct" that with `uncheck` — that clears the row for good, and re-ticking it is then the reviewer's job, not yours.
- **Re-read after a ripple.** The digest only re-opens a file whose own bytes changed. When an unchanged file's correctness now hinges on a file that did change, run `chapter-review uncheck --path <file>` so its checkmark drops and the reviewer looks again. This is a real uncheck: the box stays unreviewed until they re-tick it, unlike a finding, which leaves the box green.

## Quality rules

- **Title**: imperative, ≤ 60 chars. "Add OIDC provider", not "OIDC stuff".
- **Description**: only when *why* isn't obvious from the title. One or two sentences. Don't recap the file list — the tree shows it.
- **Per-file `note`**: only when a file is split (across chapters, or between a chapter and `unassigned`) and the chapter-side entry's scope isn't obvious. Otherwise omit.
- **No filler chapters.** "Misc cleanup" is a smell — either it's a real refactor (name it) or it belongs in `unassigned`.

## Schema

The contract is `chapters.schema.json` (draft-07) and the worked example is `example-chapters.json`, both next to this SKILL.md. `validate.ts` (also here) enforces it and is authoritative if the two ever disagree. Key semantics beyond the obvious:

- A file entry **without** `hunks` claims the file's entire diff, so you don't enumerate ranges. Omit `hunks` whenever all of a file's changes belong to one chapter: added and deleted files are the obvious case, but a *modified* file whose hunks all land in the same chapter should omit them too. Reach for `hunks` only when a file splits across chapters (or between a chapter and `unassigned`); then only those ranges are claimed and the file may appear elsewhere with disjoint hunks.
- Splitting a file between a chapter and `unassigned` is normal (e.g. one real hunk plus one autoformat hunk); the disjointness rules are the same. A `note` on the chapter-side entry flags which part is the real change, on the same threshold as every other note (see [Quality rules](#quality-rules)): add one only when the entry's scope isn't already obvious from the tree, otherwise omit. The unassigned side carries only its `reason` (the schema forbids `note` there).
- A renamed file's content hunks are absorbed by its whole-file claim; enumerate them only if they must split across chapters, then treat it like any modified file (with `oldPath` set).
- `unassigned` entries require a `reason` and are always present as an array, even when empty.
- `issues` is an optional top-level array of the skill's per-chapter review findings (id, path, optional hunk, chapterId, severity, note, confidence, status). You never write this array directly — `chapter-review issue …` owns it (assigning ids, inferring chapters, preserving across regeneration). It also owns the sibling `issueSeq`, the highest `iss-N` ever handed out, kept so a removed id is never reused; never author that either. The durable anchor is `path` (+ `hunk`); `chapterId` is the display grouping and stays stable across regen, re-mapped only when a path moves to a different chapter. `confidence` is `suspected` (default) or `verified`; see step 7.
- Checkmarks are **not** in the manifest. They live in a sibling document, `<git-dir>/chapter-review/progress.json` (`{ version, reviewed: [{ path, hunk?, digest }] }`), for the same reason `focus.json` is separate: one writer per file. The extension owns it and writes it as boxes are ticked; the CLI only reads it, except `uncheck`, which clears units from it. When both parties wrote the manifest, each side's whole-file read-modify-write could silently drop the other's edit. A manifest from an older extension may still carry a top-level `reviewed`; that is accepted and migrated into `progress.json` on the next write. You never author either. A unit reads as checked only while its `digest` matches the current content, which is what drops a checkmark when its file changes and keeps it when it doesn't.
- `version` is `1`; consumers reject unknown versions.

## Follow-up review (focus-driven)

Once the manifest exists, the user reviews in the extension and asks you questions here. Run `chapter-review focus` to see what they are currently looking at — it prints what they last clicked (a file, hunk, or issue):

```json
{ "path": "src/auth/oidc.ts", "line": 42, "chapterId": "ch-2", "issueId": "iss-3", "updatedAt": "2026-07-03T10:00:00Z" }
```

`line`, `chapterId`, and `issueId` are optional; if nothing is selected yet the command says so.

**When it applies.** Any question that leans on what the user is currently looking at is focus-driven, not just the phrases "this file / this change / this issue". It also covers "what am I looking at", "what's the problem here", "explain this", and bare follow-ups like "now?". If a question names no explicit target, assume it is about the current focus.

**How to answer.** The focus is a pointer, not the answer. Resolve it: read the referenced file (around `line` when present) and look up `chapterId`/`issueId` in the manifest (`chapter-review show`), then answer about that actual content. Resolve it defensively: `focus` reports what the file says without checking it against anything, so a pointer can name a path the partition no longer holds or an `issueId` you have since removed. When a lookup comes back empty, fall back to whatever else the pointer carries (the path and line, or the chapter) rather than reporting the id at the user — they clicked something real. Never just echo the pointer back or hand the lookup to the user. Resolve it silently: don't preface the answer by explaining that the question was focus-driven or that you consulted the focus. Just answer as if the user had named the file.

Example: the user asks "what's wrong here?" and the focus points at `foo/bar.ts` / `iss-1`. Read the file and the `iss-1` note, then explain the finding against the code, not "you are focused on iss-1".

On request, add or revise findings with `chapter-review issue add` / `issue set <id>` / `resolve <id>` / `reopen <id>` / `verify <id>` / `unverify <id>` / `rm <id>`; each validates and installs on its own. This is where a suspected finding gets closed out: `issue verify` one whose premise now holds, `issue rm` one that didn't. To send the reviewer back to something, `chapter-review uncheck --path P` drops its checkmark. The focus is transient state owned by the extension; read it with `chapter-review focus`, never write it.

**`iss-` findings are local; acting on them is out of scope.** `chapter-review issue` is the skill's own finding list for this branch, filled as you read the diff and whenever the user later asks (regeneration included, via the re-read pointers above). What a reviewer does with a finding, opening a PR comment, filing a tracker issue, fixing the code, or writing a report, is downstream and out of scope here. So a request to draft a PR comment or file a tracker issue produces a deliverable for that external system; despite the shared word "issue", it does not add an `iss-` entry.

## Installing in another repo

This skill directory is self-contained: `SKILL.md`, the `chapter-review` command (a shebang shim over `main.ts`, which dispatches to the sibling `.ts` modules `git.ts`, `manifest.ts`, `flags.ts`, `util.ts`, `cmd-*.ts`, and `validate.ts`, with shared types in `types.ts` and a `package.json` that marks the folder as ESM), `chapters.schema.json`, and `example-chapters.json`. The shim holds no logic on purpose: Node only strips types from `.ts`/`.mts`/`.cts`, so an extensionless entry file can carry neither types nor type-checking, and keeping dispatch in `main.ts` puts it under both the compiler and the linter. Copy the whole `chapter-review/` folder into that repo's `.claude/skills/`. Requirements are `git` and `node` 22.18 or newer on PATH; the CLI is TypeScript that Node runs without a build step or `npm install`. The `tsconfig.json` and `@types/node` in the folder type-check the source and aren't needed to run it. Pair it with the chapter-review VSCode extension to review the generated manifest.

## Known limitations

- **No commit-splitting.** This skill only describes the diff. Rewriting history into one-commit-per-chapter is out of scope.
