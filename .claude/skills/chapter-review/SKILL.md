# Chapter review

Partition the current branch's diff into logical chapters and hand them to the extension with the `chapter-review` command that sits next to this file. You never read or write the manifest file yourself: `chapter-review write` installs a partition draft, `chapter-review issue …` records findings, and `chapter-review focus`/`show` read back the review state. The command owns the protocol directory (`<git-dir>/chapter-review/`: `chapters.json` for the current round's partition and every finding, `progress.json` for the reviewer's checkmarks in it, `rounds/<n>/` for earlier review rounds, `focus.json` for what they're looking at, and a `chapters.json.bak` refreshed before each write), validates every change, and preserves findings and review progress across regeneration — so you talk to the extension, not to a file.

Every hunk must end up in exactly one chapter — or in `unassigned`. The contract is `validate.ts` (authoritative) and `chapters.schema.json` (the same rules as JSON Schema), both next to this file; `example-chapters.json` next to them is a worked illustration. The manifest lives inside the git dir on purpose: it is tool state, invisible to `git status`, and no user-owned file (worktree, `.gitignore`, `.git/info/exclude`) gets touched.

## The command

**Read [COMMANDS.md](COMMANDS.md) next to this file for the full reference** (every command, its flags, and the manifest field semantics). The three things you cannot get wrong:

- **Invoke it as `node "<path>/chapter-review" <args>`**, building `<path>` yourself from this file's own location. No `$SKILL_DIR` is exported, and on Windows the file is never executable, so the `node` form is the only one that always works.
- **Run it with your current directory inside the repo you're reviewing.** It takes its manifest destination from `git rev-parse --absolute-git-dir` at the cwd, not from where the command lives, so a cwd in the wrong worktree silently writes into the wrong `.git`. `write` prints the path it wrote; check it.
- **`chapters.json` is yours; `progress.json` and `focus.json` are the extension's**, and your own commands must run **serially** — each reads the manifest, changes one thing and writes it back, so two racing invocations drop one change and both report success.

Commands: `write [file] [--dry-run]` installs a partition draft, `issue add|set|resolve|reopen|verify|unverify|rm|list` records and revises findings, `uncheck` clears a checkmark, `base-check [base]` reports base freshness, `focus` and `show` read the current state. Every mutating command validates before writing and refuses an invalid result, so there is no separate validate step. Requirements are `git` and `node` (22.18 or newer) on PATH.

**When the chapter-review MCP tools are available, use them instead of invoking the command.** The extension registers them with Claude Code when it installs this skill, under the server name `chapter-review`: `focus`, `show`, `base_check`, `write`, `uncheck`, `issue_add`, `issue_set`, `issue_list`, and `issue_update`, whose `action` is `resolve`, `reopen`, `verify`, `unverify` or `rm`. Each tool runs the command and returns its output unchanged, so this file and COMMANDS.md hold as written: read `chapter-review <command>` as the matching tool, with flags as named fields (see [COMMANDS.md](COMMANDS.md#as-mcp-tools)). Two things differ. Every tool takes `repo`, the absolute path of the repository you're reviewing, in place of your current directory, so the cwd rule above becomes "pass the right `repo`". And `write` takes the draft inline as `draft` or as a `file` path, with `dry_run: true` for the dry run. The server runs its calls one at a time, which keeps the serial rule for you as long as you don't mix tool calls with command invocations. Without the tools, use the command.

## Steps

1. **Resolve refs, then confirm the base is fresh.** `base` = default branch (check `git symbolic-ref refs/remotes/origin/HEAD`; if this errors for any reason — no origin remote, or an origin that never ran `remote set-head`, which both report `not a symbolic ref` — fall back to `main`, then `master`, taking the first that `git rev-parse --verify` actually resolves rather than assuming it exists), `head` = current branch, `headSha = git rev-parse HEAD`. `base` and `head` are ref names, `headSha` is a full SHA.

   **Keep the `origin/` prefix when `origin/HEAD` resolved it.** Strip only `refs/remotes/`, so `refs/remotes/origin/main` → `base = "origin/main"`, not the local `main`: the tracking ref is what a PR merges into, and it's what a bare `base-check` resolves, so recording it keeps base-check judging the ref you diff against. Only the fallback chain yields a bare local name, having no tracking ref to prefer.

   Before taking the diff, run `chapter-review base-check` (pass your resolved base, or omit it to let the command resolve it the same way). A stale base is the classic footgun: an unfetched `origin/main` pushes the merge base back to an old fork point, so the diff fills with commits already merged to main. Branch on its `action`:
   - `"ok"` — proceed. If `remoteReachable` is `false` (remote unreachable) or `null` (no origin), the remote check was skipped: proceed, and **say so in your reply to the user**. That is the one reporting duty on the happy path. Only an `"ok"` carries `round`, the review round the next `write` makes:
     - `number`: 1 on a first review, one more for each push reviewed since.
     - `new`: true when the write starts this round, a first review included; false when the head has not moved since the last write, so you are re-partitioning.
     - `diff`: the command whose output this round partitions, starting at `fromSha` (the merge base in round 1).
     - `chapters`: on a later round, the chapter ids used so far, to reuse. See [Regenerating](#regenerating-the-branch-moved).
   - `"switch"` — a fresher local base exists. Set `base = suggestedBase` and continue; it's a local ref with no fetch, so don't ask, just mention the switch in your reply. ("Your reply" throughout means prose back to the user, not the manifest's `summary` field.)
   - `"fetch"` — `origin/<branch>` is unfetched. Ask the user, in prose, whether to `git fetch` and regenerate against the fresh fork point or proceed against the stale base. Fetch only on their go-ahead.
   - `"unresolved"` — nothing resolved. Don't re-run the resolution above; that chain is what failed. Ask the user in prose, listing local branches that aren't `head`. If there genuinely is no other branch, say so and use the root commit (`git rev-list --max-parents=0 HEAD`) as `mergeBase`, recording that `base` so the reviewer sees what the diff was taken against.

   Take `mergeBase` (a full SHA) and `round` from the `ok` answer for the base you settled on: `base-check` computes them the way `write` will, so don't derive them again. The diff runs from `round.fromSha`, never from `base`: you want "what this branch added", not "what main looks like vs me". Always record `headSha`: the extension reconstructs chapter-scoped diffs from it after the branch moves on. Resolve all of this fresh on every run, a regeneration after the branch moved included (see [Regenerating](#regenerating-the-branch-moved)); never carry a previous run's refs forward.

2. **Pull the diff.** Run the `round.diff` from step 1, which on a first review is `git diff -M --unified=3 <mergeBase>..HEAD`. `-M` matters: without it a rename shows up as delete+add and can never become `status: "renamed"`. Parse files and hunk headers (`@@ -oldStart,oldLines +newStart,newLines @@`). Header quirks: a count of 1 is omitted (`@@ -3 +3,2 @@` means `oldLines: 1`), and the empty side of an added/deleted file reads `-0,0` / `+0,0`.

3. **Cluster by intent, not by file.** A chapter is what a reviewer evaluates as one unit: "remove legacy X", "add Y", "rename Z everywhere", "tests for Y". One file can split across chapters; one chapter can span many files. Aim for 3–8 chapters on a typical branch — 15 means you're slicing too thin, 1 means too coarse. On a small branch fewer is fine; never pad the count.

   Chapters must be self-contained: the reviewer should see a change *and* what it means in one sitting.
   - Don't split an abstraction from its implementation and wiring. An interface, its first implementation, and the injection sites are one chapter unless each is genuinely large.
   - When the branch replaces X with Y, keep the removal of X visible: either one "replace X with Y" chapter, or a "remove X" chapter directly next to the "add Y" chapter. Never tuck the deletion of X into a chapter whose title is about Y's wiring.
   - **A lone renamed call-site stays with the substantive change.** When one file carries both a substantive change and a single renamed call-site, that hunk belongs where the substance is. Only pull call-sites into the rename chapter when the rename is that file's main change. So a rename rippling across files is its own chapter, but never split a file just to relocate one call-site out of it. Keeping the call-site usually leaves that file wholly inside one chapter, and a wholly-owned file **omits `hunks` entirely** even when the diff shows several — don't enumerate ranges you don't need to split on (see [COMMANDS.md](COMMANDS.md#schema)). Granularity is not a free choice: flipping a file between whole-file and hunk-split re-keys the reviewer's checkmarks on it, so decide it by this rule and keep the decision stable across regenerations. Noise overrides all of this, and you don't need step 4 to settle it: when a file carries one real hunk plus one pure-autoformat or generated hunk, split it — real hunk to its chapter, noise hunk to `unassigned` with a `reason` — even though that means enumerating ranges. Quarantining noise is not "relocating a call-site", so the two rules never actually compete. If the rename chapter ends up holding only the renamed file itself and no call-sites, keep it — a one-file rename chapter is fine, and its `description` should say where the call-sites went ("call-sites travel with their own chapters").
   - A chapter whose files can't be understood without opening a later chapter is mis-cut.

4. **Quarantine noise.** Lockfiles, snapshot updates, generated code, pure autoformat hunks → `unassigned` with a short `reason`. Don't force these into thematic chapters.

   A generated file's *driver* is not noise: a version bump in a csproj or package.json is a hand edit and belongs in a chapter (its own chore chapter, or the chapter that needed the bump), while the lockfile it regenerates goes to `unassigned` with a reason naming the driver **by path**. The path is the whole anchor, and it is enough: say "regenerated by the bump in Demo.csproj" and stop. Don't reach for which chapter that path landed in — you cannot name it (see below), and the reviewer finds the file by path anyway. Don't cite a chapter id in `reason` prose: ids are stable only within a generation and may be reminted on the next one, and nothing rewrites prose that references them, so a cited id silently goes stale.

5. **Check completeness.** `⋃(chapter hunks) ∪ unassigned == full diff`. `write` enforces this in the next step and names every offending file and range, so you don't audit it by hand: it refuses an unclaimed file or hunk, a range the diff doesn't have, a path outside the diff, and a `status` git disagrees with. Take `status` from the diff rather than deciding it, since the extension renders an `added` entry with an empty left-hand side and a modified file labelled that way loses its before-diff.

   Copy hunk coordinates from the `@@` headers rather than counting lines: the extension reconstructs each chapter's diff from exactly those numbers. Coverage is judged on the lines the diff changed rather than on hunk spans, so a coordinate that slides off a changed line is caught, but one that merely widens a hunk into neighbouring context is not.

6. **Order chapters as a review flow.** The order *is* the narrative: at every chapter the reviewer should know why they're looking at it. Core change first — the thing the branch exists for, with a preceding removal only when it motivates what follows. Independent side changes (mechanical renames, opportunistic refactors) come after the core story, not before it; leading with a trivial rename buries the plot. Then tests, then docs/chores.

   Story test before writing: read your titles top to bottom. They should work as a changelog that explains the branch to someone who hasn't seen the diff. If any title raises "why is this here / why now?", re-order or re-merge. A tooling or test-framework bump (an xunit upgrade, say) can sit with the tests it supports or as a trailing chore; either reads fine.

7. **Note the issues you noticed.** Partitioning means reading the whole diff, so keep track of genuine problems as you go: bugs, risky changes, smells, or things worth questioning. You'll record them with `chapter-review issue add` in step 9 (it needs the manifest to exist first). Each finding is a `path`, a `severity`, a one-line `note`, and, when it is about specific code, a `--line`: the 1-based line of the file at HEAD that the finding is about, which is where clicking the finding puts the reviewer. Pass it whenever the note points at a statement, a declaration or a comment, **including in an added file**, whose one hunk spans the whole file and so says nothing about where the problem is, and in a long hunk, whose first change can sit far from the line in question. When the problem shows on one line and its fix belongs on another, anchor on the line the fix has to change, since that also files the finding under the chapter the fix will land in: a signature that drops a parameter rather than the call that suffers for it, the line in the test where the missing assertion would go rather than the untested call. Something missing takes the line its fix would start from, such as the declaration nothing consumes yet, and a fix that would live in a file not yet written takes the line in existing code it would connect to. Code the fix would add at the end of a block anchors on the block's last statement, not its closing brace. When two lines fit equally well, either is right: take the one a reader meets first. Copy the line from `git show HEAD:<path>`, never by counting `+` lines in the diff. On a file the partition splits into ranges, the line also picks the range the finding is pinned to and the chapter owning it; on a file claimed whole it stays a bare line, which is all the extension needs. Pin a `--hunk` instead only for a finding about a whole range rather than a line in it, copied from the diff (a range that is neither claimed nor in the diff is refused); given both, the line must lie inside the range. A finding genuinely about the whole file (a deleted file, a file that should not exist) takes `path` alone. The id and the owning chapter are assigned for you.

   **One problem per finding.** Two problems in one note get one severity, so the lesser one arrives inflated, and `issue resolve` then closes both or neither even though only one of them was fixed. The test is the fix: what needs two separate edits is two `issue add` calls, in the same hunk included, and each one is rated on its own harm. A null deref on a new path and a leftover debug log two lines below it are a `high` and a `low`, not one `high` note joined by "and also". The exception is a second thing that follows from the first, one mechanism and one edit for both, where the note names the mechanism once instead of listing everything downstream of it.

   **A file the branch left wrong without changing it gets the finding itself.** A stale doc, a config or a caller the branch forgot is outside the diff and has no hunk, so record it with `--path <that file> --line <n>` and name the change responsible with `--cause-path` (plus `--cause-hunk` when that file is split across chapters). The finding is filed under the chapter owning the cause, so the reviewer meets it while reading the change that broke it, and opening it shows the stale file at that line. Never anchor such a finding on the changed file with the stale one named in the note: the reviewer then lands on code the finding isn't about. Copy the line from the file at HEAD. Without a cause the finding has no chapter, so give one whenever the change behind it is in the diff, which it nearly always is. See [COMMANDS.md](COMMANDS.md#findings-outside-the-diff).

   Severity: `critical` = broken or unsafe as written (data loss, security hole, crash on a normal path); `high` = a real bug or risk that bites on a real path; `low` = a smell, gap, or minor concern. Judge the change as written, but don't flag an intentional simplification as if it were a production omission unless the branch presents itself as complete.

   **When "is this meant to be complete?" has no answer, rate by the branch's own intent.** Demos, fixtures, spikes and sample repos give that question no purchase, and the same finding is then defensible at two severities, so the tiebreaker is whether the gap defeats **the thing the branch set out to do**. A branch adding an LRU cache whose entries are never evicted fails its own premise, so that is `high` however toy the surrounding repo is; a stray debug log in the same file is `low` there and `low` in production, because it was never the point. Rate the placeholder that stayed a placeholder `low`, and the new code that doesn't do its one job `high`. Don't split the difference to hedge, and don't discount a finding because the repo is a sample.

   Flag only real findings; a clean chapter has none, and findings never block writing the manifest. The user reviews these and can ask you to add or revise more later (see Follow-up review).

   Confidence is separate from severity, and the test is **where you had to look**, not how sure you feel. Mark a finding `verified` (`--confidence verified`, or `issue verify` later) only when you went *outside the diff you were partitioning* to confirm it: opened a file at HEAD, traced a caller, searched the repo. Reading another hunk of the same diff doesn't count, since a partition pass reads the whole diff anyway. Anything visible entirely inside the diff stays `suspected`, the default, because the diff shows what changed and not what the rest of the codebase does about it. So most findings stay `suspected`, and that's expected: verifying every one would turn partitioning into an audit.

8. **Install the partition.** Build the draft — `version: 1`, `base`, `head`, `mergeBase`, `headSha`, ISO-8601 `generatedAt` (any valid placeholder works; `write` re-stamps it), no `round` or `fromSha` (`write` sets both from what `base-check` reported), an optional `summary` (one or two sentences on what the branch does overall, shown as the branch summary in the extension; on a later round, what that round changed instead, see [Regenerating](#regenerating-the-branch-moved); same omit test as a `description`, applied to the whole branch — write one when no single chapter title accounts for everything the branch does, which is nearly always true once there are several chapters, and omit it when the summary would just restate chapter one), `chapters` (each with a stable `id`: number them `ch-1`, `ch-2`, … on a first write, starting at 1 because `ch-0` is refused (0 is the issue sequence for findings no chapter owns), and on a regeneration reuse the ids `base-check` lists in `round.chapters`, see [Regenerating](#regenerating-the-branch-moved)), and `unassigned` — and hand it to `chapter-review write` (write it to a scratch file and pass the path, or pipe it on stdin). Keep that scratch file **anywhere but under the worktree root** you are reviewing, or pipe on stdin: a draft written inside the worktree gets picked up by the next `git add -A` and committed into the branch under review. A sibling or parent directory is fine.

   **Run `chapter-review write <draft> --dry-run` first, then the same command without it.** The dry run performs every check and prints the identical report (opening `Would write …`, including the coverage verdict and the claim counts) while installing nothing, so you see what the partition does before it lands. A draft that passes `--dry-run` installs.

   Do **not** put an `issues` array in the draft; findings are recorded separately in step 9, and the reviewer's checkmarks live in `progress.json`, which the extension owns. The command validates and refuses a broken partition (fix and re-run), then prints the summary line — relay it, don't echo the JSON. On regeneration it carries existing findings and checkmarks forward for you; nothing to preserve by hand. It also re-pins `headSha`/`mergeBase`/`generatedAt` to the commit it sees, so the manifest matches live git and the extension's "Review may be out of date" banner clears once the write lands.

9. **Record the findings.** Run `chapter-review issue add --path … --severity … --note "…"` once per problem from step 7, so two problems joined by an "and" are two calls, while a consequence of the same mechanism stays in its note (step 7's exception). Add `--line N` for every finding about specific code (see step 7). The owning chapter is inferred from the path and the line; when the path spans several chapters and the line sits in none of their ranges, add `--chapter ch-N`, and the command warns if it has to guess. A finding about a whole range takes `--hunk oldStart,oldLines,newStart,newLines` instead, which selects the chapter owning that range and pins the finding to it. Add `--confidence verified` only for findings that met step 7's test — you looked outside the diff to confirm them. Skip this step when the branch is clean.

10. **Hand over at chapter 1.** Relay the `write` summary line, list the chapter titles in order with each one's open finding count, and invite the reviewer to start reading chapter 1. Don't spell out the findings themselves yet; [Walking the chapters](#walking-the-chapters) says when they come up.

## Regenerating (the branch moved)

Re-running the skill on a branch that already has a review is a normal operation: after the author pushed fixes and the reviewer pulled, after an amend, or after a rebase. Resolve refs fresh (step 1) as always; the `round` that `base-check` reports then says which of two cases you are in.

**A new round** (`round.new` is true): the head moved since the last write. The review gains a round holding only what changed since the previous one, so the reviewer reads the author's fixes rather than the whole branch again. Partition `round.diff`, which is `git diff -M --unified=3 <round.fromSha>..HEAD`, the usual way, never the whole branch: `write` refuses a partition of anything else. The draft holds only the chapters this round's changes fall into: a chapter the round does not touch stays out of it and lives on in its earlier round. Reuse an id from `round.chapters` for a change that belongs to an existing chapter, as a fix to a file a chapter held usually does, so the same `ch-N` names the same chapter in every round; mint the next unused id only for genuinely new material. Give the round a `summary` of what the author changed in it ("Fixups: drain the queue, drop the debug print"), since the extension shows the current round's summary at the top of the view. When the author also rebased onto a moved base, `fromSha` is their previous head replayed onto the new base, so the base's own changes stay out of the round; a file the replay conflicted on (`round.replayConflicts`) keeps the previous version, and its round diff also shows what the base changed there. `write` keeps the previous round as it was, with its checkmarks, takes along every open finding on a file the new round changes, re-anchored onto it, and leaves the other findings in their round. It names the findings that came along with their own line untouched: re-read each one against the round's diff, since a fix can land on new lines without touching the finding's own, and then no other list in the report mentions it. When a fix covers only part of a finding, `issue set` its note down to the part that is fixed and resolve it, then `issue add` the rest as its own finding. A reused chapter keeps its title, so the reviewer recognizes it across rounds; the round's `summary` is where the fixups are described. Never re-partition an earlier round.

**The same round** (`round.new` is false): nothing new was committed and you are re-partitioning, to fix a draft or regroup. Don't rebuild from scratch: run `chapter-review show`, keep each file in the chapter it already lived in and carry that chapter's `id` across; mint a new id only for a genuinely new grouping. `show` prints the installed manifest, which makes a ready starting draft once you drop its `issues` and `issueSeq` (a draft carrying them is refused). When nothing about the grouping changes, resubmit the previous draft exactly as it was, since `write` re-pins it.

You call the same `chapter-review write` as on a first run. It re-pins the commits and the round, carries findings and checkmarks forward, and never renumbers the ids you supply; [COMMANDS.md](COMMANDS.md#write) has the mechanics. What that leaves you to do:

- **Build the partition against the current HEAD**, since that is what `write` pins to. A stale partition stamped with a fresh HEAD renders diffs against the wrong blobs.
- **Give a renamed file `status: "renamed"` and `oldPath`.** `oldPath` is the rename-from path *this* round's diff reports, never a path carried over from the previous manifest. Findings then follow the file to its new path (`write` prints `followed rename …`); omit `oldPath` and the rename reads as a delete plus an add, losing exactly the review work you were preserving. A file the branch added and *then* renamed within the round arrives as a plain `added` entry under its final name, with no rename for `-M` to find.
- **Review what the new commits changed, and add findings only for genuinely new problems.** A fix can introduce a problem of its own, and `write` reports only on findings that already exist. Carried-forward ones are already there, so check `chapter-review issue list` before adding.
- **Expect a finding whose chapter changed to be renumbered.** An id counts in its chapter's sequence, so when the new partition hands a finding to another chapter it takes the next id there and `write` prints `renumbered iss-1.2 -> iss-3.1 (ch-3)`. Relay those lines: the old id may be quoted in a PR comment or earlier in this conversation, and the mapping is the only way back to it. Both numbers stay retired, so neither is handed out again.
- **Act on the findings `write` lists as no longer anchored.** When the range a finding was pinned to leaves the diff, usually because the author fixed exactly that hunk, nothing in the new partition covers it and the coordinates stay as they were. Re-read each one against the current diff: `issue resolve <id>` if the change it named is gone, or `issue set <id> --hunk …` onto the range it belongs to now. Left alone the finding still lists and still shows in its chapter, but points into code no chapter claims, so opening it lands nowhere in particular.
- **Act on the findings whose own line changed.** A finding's line moves with the code around it, and `write` lists the open ones whose line itself was touched: "edited since" when other lines replaced it, "removed" when nothing did. Read the change at each one. A removed line usually means the author fixed exactly that, so `issue resolve <id>`; `write` has already dropped the line, keeping the range. An edited one is the fix or not depending on what it now says, and a finding whose problem still stands on its line needs nothing. If the problem still stands but sits elsewhere, `issue set <id> --line <n>` onto it. A `verified` finding whose line changed stays verified only once you have re-checked its premise; `issue unverify <id>` otherwise.
- **`N checkmarks carried` is not a signal to act on.** It only appears when re-partitioning the same round, and counts rows that survived path-pruning; whether one still *reads* as reviewed is decided against content by the extension. A new round starts unticked by design, while earlier rounds keep their ticks. Don't "correct" either with `uncheck`, which clears a tick for good and makes re-ticking the reviewer's job.
- **Do reach for `uncheck` after a ripple.** When an unchanged file's correctness now hinges on one that changed, `chapter-review uncheck --path <file>` sends the reviewer back to it in the round that holds it, and the box stays unreviewed until they re-tick it.

## Quality rules

The schema states which of these fields are optional and their limits; these are the tests for whether to write one at all.

- **Description**: test it by asking what a reader still doesn't know once they've read the title. "Rename Guard to Ensure" doesn't say where the call-sites went, so that chapter earns one, which is why step 3 asks for it: that's this rule applied, not an exception to it. "Replace EmailNotifier with a queued INotifier" already carries its own why, so "this swaps the notifier for a queue-backed one" is filler. If the only sentence you can write restates the title, omit the field.
- **Per-file `note`**: a split does not earn a note by being a split. If the `unassigned` side's `reason` already says what the other part is ("pure autoformat"), the chapter side needs nothing. Write one when a file splits across *two chapters* and neither title says which half is which.
- **No filler chapters.** "Misc cleanup" is a smell — either it's a real refactor (name it) or it belongs in `unassigned`.

## Schema

The contract is `chapters.schema.json` (draft-07), the worked example is `example-chapters.json`, and `validate.ts` enforces it and wins if the two disagree. All three sit next to this file. The example is a manifest as it looks *after* `issue add` has run, not a draft template: it carries an `issues` array, which `write` refuses in a draft (see step 8), so copy the partition fields out of it and leave `issues` and `issueSeq` to the CLI. **[COMMANDS.md](COMMANDS.md#schema) explains the field semantics**; the one rule you need while partitioning is that a file entry **without** `hunks` claims that file's entire diff, so you only enumerate ranges when a file genuinely splits.

## Walking the chapters

The review goes one chapter at a time, in manifest order.
Each chapter has two phases: first the reviewer reads the code, then you go through the chapter's findings together.
Keep them in that order and don't run ahead into the next chapter.
Findings read before the code shape how the code gets read, which is why step 10 hands over with counts only.

**Reading phase.**
The reviewer opens the chapter's files and asks questions, which you answer as [Follow-up review](#follow-up-review-focus-driven) describes.
Answer the question asked and don't bring up the chapter's recorded findings unprompted.
When a question lands on code a recorded finding already covers, name that finding's id in one line so the reviewer knows it is queued, and keep the discussion for the findings phase.
When the reviewer raises a new problem, record it with `issue add` right away.
It lands in whichever chapter owns the path, and that is often not the chapter being read, so say which chapter it went to and carry on with the reading.

**Findings phase.**
It starts when the reviewer says they are done reading ("done with the files", "let's go through the issues", "findings?").
Wait for that signal: a focus that wanders into another chapter's file is usually a look for context, not a switch.
Run `chapter-review issue list` and take the chapter's open findings in id order, the ones added during reading included.
Present one finding per message: where it sits and the mechanism, against the code as it is now.
Then wait for the reviewer's decision and apply it before moving on: keep it open as written, revise it (`issue set`), `verify` or `unverify` it, `resolve` it, or `rm` it.
When the last one is settled, say the chapter is done and name the next chapter, whose reading phase starts next.

**Findings that land behind you.**
A finding added while reading chapter 4 that belongs to the finished chapter 2 would never get a findings phase of its own.
Take it up at the end of the current chapter's findings phase, after the chapter's own, and do the same for an `iss-0.N` finding no chapter owns.
A finding that belongs to a later chapter waits for that chapter.

**Leaving the order.**
The reviewer can jump to another chapter or ask about a finding out of turn at any point; follow them.
The chapter they left keeps its open findings for when they come back, and you pick the order up again from there.
When the last chapter is done, list what is still open, grouped by chapter, so nothing is left without an outcome.

## Follow-up review (focus-driven)

Once the manifest exists, the user reviews in the extension and asks you questions here. Run `chapter-review focus` to see what they are currently looking at — it prints what they last clicked (a file, hunk, or issue):

```json
{ "round": 2, "path": "src/auth/oidc.ts", "line": 42, "chapterId": "ch-2", "issueId": "iss-2.3", "updatedAt": "2026-07-03T10:00:00Z" }
```

`line`, `chapterId`, and `issueId` are optional; if nothing is selected yet the command says so. `round` is the review round the selection belongs to, and the line is that round's head's: in an earlier round, read the file with `git show <that round's headSha>:<path>` (from `rounds/<n>/chapters.json`) rather than from the working tree.

**When it applies.** Any question that leans on what the user is currently looking at is focus-driven, not just the phrases "this file / this change / this issue". It also covers "what am I looking at", "what's the problem here", "explain this", and bare follow-ups like "now?". If a question names no explicit target, assume it is about the current focus.

**How to answer.** The focus is a pointer, not the answer. Resolve it: read the referenced file (around `line` when present) and look up `chapterId`/`issueId` in the manifest (`chapter-review show`), then answer about that actual content. Resolve it defensively: `focus` reports what the file says without checking it against anything, so a pointer can name a path the partition no longer holds or an `issueId` you have since removed. When a lookup comes back empty, fall back to whatever else the pointer carries (the path and line, or the chapter) rather than reporting the id at the user — they clicked something real. Never just echo the pointer back or hand the lookup to the user. Resolve it silently: don't preface the answer by explaining that the question was focus-driven or that you consulted the focus. Just answer as if the user had named the file.

Example: the user asks "what's wrong here?" and the focus points at `foo/bar.ts` / `iss-1.1`. Read the file and the `iss-1.1` note, then explain the finding against the code, not "you are focused on iss-1.1".

**A bare number the user quotes is an id.** The extension labels every chapter row with its number and every finding with its own, so those numbers are what the user has in front of them. A number with a dot is a finding and a plain one is a chapter, which is all you need to tell them apart: "1.2" or "the second finding in chapter one" means `iss-1.2`, while "chapter 2", "ch 2" or a bare "2" means `ch-2`. Look a chapter up in `chapter-review show` and a finding in `chapter-review issue list`, then answer about that content. When a number names nothing (a regeneration may have renumbered it, or removed the finding), say which id you looked for and offer the nearest one rather than guessing at another.

On request, add or revise findings with `chapter-review issue add` / `issue set <id>` / `resolve <id>` / `reopen <id>` / `verify <id>` / `unverify <id>` / `rm <id>`; each validates and installs on its own. Step 7's one-problem-per-finding rule holds here too: a question that surfaces two problems in one file yields two `add` calls, and when the user asks about a finding that already bundles two, `issue set` the note down to one problem and `add` the other separately rather than leaving the pair on one severity. This is where a suspected finding gets closed out: `issue verify` one whose premise now holds, `issue rm` one that didn't. To send the reviewer back to something, `chapter-review uncheck --path P` drops its checkmark. The focus is transient state owned by the extension; read it with `chapter-review focus`, never write it.

**`iss-` findings are local; acting on them is out of scope.** `chapter-review issue` is the skill's own finding list for this branch, filled as you read the diff and whenever the user later asks (regeneration included, via the re-read pointers above). What a reviewer does with a finding, opening a PR comment, filing a tracker issue, fixing the code, or writing a report, is downstream and out of scope here. So a request to draft a PR comment or file a tracker issue produces a deliverable for that external system; despite the shared word "issue", it does not add an `iss-` entry.

## Installing in another repo

This skill directory is self-contained: `SKILL.md`, `COMMANDS.md`, the `chapter-review` command (a shebang shim over `main.ts`, which dispatches to the sibling `.ts` modules `git.ts`, `manifest.ts`, `flags.ts`, `util.ts`, `cmd-*.ts`, and `validate.ts`, with shared types in `types.ts` and a `package.json` that marks the folder as ESM), `chapters.schema.json`, and `example-chapters.json`. `COMMANDS.md` is part of the contract, not an extra: `SKILL.md` defers the command and field reference to it. The shim holds no logic on purpose: Node only strips types from `.ts`/`.mts`/`.cts`, so an extensionless entry file can carry neither types nor type-checking, and keeping dispatch in `main.ts` puts it under both the compiler and the linter. Copy the whole `chapter-review/` folder into that repo's `.claude/skills/`. The folder also holds `mcp.ts`, which serves the same commands as MCP tools; registering it is optional (`claude mcp add --scope user chapter-review -- node <path>/mcp.ts`), and the skill works without it. Requirements are `git` and `node` 22.18 or newer on PATH; the CLI is TypeScript that Node runs without a build step or `npm install`. The `tsconfig.json` and `@types/node` in the folder type-check the source and aren't needed to run it. Pair it with the chapter-review VSCode extension to review the generated manifest.
